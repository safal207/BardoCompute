# BardoCompute hardware v0.1 — BARDO-TX1

## Decision

The first hardware target is **not** a new universal CPU. It is a narrow,
streaming transition-state coprocessor for workloads where direction,
continuity, settling, and a joint policy are on the hot path.

This boundary follows the strongest current evidence:

- the six line states already have a stable three-bit contract;
- all `6^3 = 216` valid trigrams fit in one byte;
- continuity provenance has demonstrated correctness utility;
- native speed results are compiler-sensitive, so a CPU defeat cannot be
  claimed from software or core-only rooflines.

## BARDO-TX1 v0.1 datapath

```text
9 bits / lane
[upper 3][middle 3][lower 3]
              |
              v
      validate six-state codes
              |
       +------+------------------+
       |                         |
       v                         v
 sparse->radix-6            semantic features
  index 0..215          transition / discontinuity /
       |                     target count / settle
       +--------------+----------+
                      v
            fail-closed reference policy
                      |
             one registered stage
```

The top is parameterized by `LANES` and defaults to eight. It uses a
ready/valid streaming interface and holds its output stable under backpressure.
An invalid line code (`001` or `111`) makes that lane invalid and zeros every
derived field, including the policy result.

## Exact state contract

The line-code-to-radix digit map is frozen as:

| Packed code | Meaning | Digit |
| --- | --- | ---: |
| `000` | stable 0 | 0 |
| `010` | rising, continuous | 1 |
| `011` | rising, discontinuous | 2 |
| `100` | falling, continuous | 3 |
| `101` | falling, discontinuous | 4 |
| `110` | stable 1 | 5 |

For ordered lines `(lower, middle, upper)`:

```text
index = lower_digit + 6 * middle_digit + 36 * upper_digit
```

The built-in reference policy is:

```text
valid
and no discontinuity
and target_count >= 2
and any actual transition
```

The core also exposes the primitive features so later wrappers can implement a
programmable policy table without changing the encoding contract.

## What “competes with a CPU” means

BARDO-TX1 only passes the competition gate when it beats the best equal-
information CPU implementation on a bounded workload. The comparison must
include the interface and setup cost, not only the combinational core.

Required controls:

1. identical input states and identical policy semantics;
2. optimized scalar/SIMD CPU paths with correctness verified outside timing;
3. warm-cache and streaming/out-of-cache regimes;
4. host-to-device transfer and setup cost for a discrete FPGA;
5. throughput, p50/p99 latency, energy per accepted trigram, logic area, and
   bytes transferred;
6. fail-closed invalid-state tests;
7. a physical measurement bound to the exact CI bitstream SHA-256.

Initial success threshold requires the complete evidence set:

- at least `2x` end-to-end throughput per watt **and**
- at least `2x` p99 latency improvement at measured throughput within `5%`,

on at least one real transition-heavy workload. A declarative
`equal_throughput=true`, a higher clock, an on-chip self-test, or a synthetic
LUT win is not sufficient.

## ULX3S implementation profiles

The physical oscillator remains 25 MHz. The repository preserves two separate
profiles so an experimental clock increase cannot overwrite the native
reference:

| Profile | Clock path | Core clock | Lanes | Core roofline |
| --- | --- | ---: | ---: | ---: |
| `native_25mhz` | board oscillator → core | 25 MHz | 71 | 1,775 Mtrigrams/s |
| `pll_25_to_75mhz` | board oscillator → ECP5 PLL → core | 75 MHz | 71 | 5,325 Mtrigrams/s |

The 75 MHz profile is generated by the pinned Project Trellis `ecppll` utility.
The Makefile rejects any generated PLL that does not retain:

```text
CLKI_DIV=1
CLKFB_DIV=3
CLKOP_DIV=8
PFD=25 MHz
VCO=600 MHz
output=75 MHz
```

It also reasserts the entire self-test reset if PLL lock is lost. Passing
place-and-route only promotes the profile to a timing-gated implementation
artifact; it does not prove that a physical board ran correctly at 75 MHz.

## Current native-profile evidence

The last reproduced 25 MHz implementation artifact reported:

```text
core roofline:              1,775.000 Mtrigrams/s
post-route achieved clock:     84.717 MHz (25 MHz constraint)
TRELLIS_COMB:                4,143
TRELLIS_FF:                  1,327
DP16KD:                          0
MULT18X18D:                      0
```

The achieved frequency is a nextpnr timing estimate, not a measured board
frequency. Inputs are generated and results reduced on chip.

The 75 MHz profile has a separate CI job, report, checksum manifest, CPU-control
report, and claim decision. Its build must independently meet the 75 MHz timing
constraint and the same zero-DSP structural contract.

## Bandwidth boundary

Exporting the complete 23-bit result for every 9-bit input would require:

| Profile | Input | Output | Round trip |
| --- | ---: | ---: | ---: |
| 25 MHz | 1.997 GB/s | 5.103 GB/s | 7.100 GB/s |
| 75 MHz | 5.991 GB/s | 15.309 GB/s | 21.300 GB/s |

This is why the useful hardware architecture must filter, aggregate, or sit
near the workload. BARDO should not become a fast core behind a slow USB
calculator boundary.

## Fair CPU control

The CPU opponent now has two admissible single-thread paths:

- materialize the complete semantic output;
- evaluate the same semantics and perform a bounded reduction.

Correctness is verified outside the timed kernels. An exhaustive table generated
from the independent Python contract is consumed by the C LUT and compared with
the direct C evaluator for all 512 inputs before timing. The strongest fair path
is retained, and a serial dependent checksum is explicitly inadmissible.

`bardocompute.cpu_control` may report core-only diagnostic ratios, but it always
leaves:

```text
cpu_competition_status=unresolved
```

## Machine-enforced claim gate

`bardocompute.hardware_claims` consumes the profile manifest, nextpnr report,
bitstream checksum, CPU control, and an optional physical measurement. The
manifest binds the bitstream, `evidence.txt`, and `nextpnr-report.json`; their
SHA-256 values are verified before claim evaluation. The gate emits JSON and
Markdown evidence and fails closed on mismatched clocks, resources, semantics,
or artifact identity.

Native profile:

```bash
PYTHONPATH=src python -m bardocompute.hardware_claims \
  --fpga-evidence fpga/ulx3s-85f/build/evidence.txt \
  --cpu-evidence hardware/build/cpu-baseline.log \
  --nextpnr-report fpga/ulx3s-85f/build/nextpnr-report.json \
  --sha256s fpga/ulx3s-85f/build/SHA256SUMS \
  --json-output fpga/ulx3s-85f/build/claim-gate.json \
  --markdown-output fpga/ulx3s-85f/build/claim-gate.md
```

PLL profile uses the same command with `build-75mhz/` paths.

The statuses are deliberately narrow:

| Status | Meaning | CPU claim allowed? |
| --- | --- | ---: |
| `CORE_ROOFLINE_ONLY` | RTL/P&R plus CPU control; no physical host stream | No |
| `PHYSICAL_SELF_TEST_ONLY` | Exact bitstream passed on-board self-test | No |
| `END_TO_END_NOT_PROVEN` | Host stream measured, but one or more gates are incomplete | No |
| `CPU_COMPETITIVE_PASS` | Exact bound artifacts, real same-workload comparison, verified equal throughput, and both 2x energy and p99 gates | Yes |

Ordinary CI requires both profiles to emit:

```text
status=CORE_ROOFLINE_ONLY
claim_allowed=false
```

`--require-competitive` is reserved for the physical release gate.

## Verification boundary

The v0.1 packet contains:

- a bit-exact Python reference model;
- exhaustive Python checks over all 512 sparse bundles;
- an RTL testbench over the same complete space;
- reset-safe ready/valid and backpressure tests;
- generic Yosys synthesis and ECP5 place-and-route;
- native and generated-PLL clock profiles;
- a DSP-free structural gate;
- bitstreams, timing reports, and profile evidence bound in one checksum manifest;
- a lane-position- and input-sensitive physical self-test signature;
- a fair optimized C control checked against an independent 512-entry oracle;
- a claim gate that cannot promote a core roofline into end-to-end speedup.

What remains unproven is physical board execution, host-fed sustained
throughput, power, temperature, p99 latency, and a real-workload CPU win.

## Hardware path

### H0 — synthesizable core: complete

Portable SystemVerilog, exhaustive simulation, generic synthesis, and a frozen
software/RTL encoding contract are present.

### H1a — FPGA implementation artifacts: complete when CI is green

The native and PLL profiles independently complete ECP5 synthesis,
place-and-route, resource/timing validation, and bitstream packaging.

### H1b — physical FPGA evidence: open

Flash an exact SHA-bound bitstream, record completed self-test epochs, measure
clock stability, power, and temperature, then add a host-fed streaming shell
with exact byte counters.

### H2 — CPU-attached execution

Two valid integration paths remain:

- memory-mapped/streaming accelerator next to a small RISC-V core;
- custom RISC-V operations for `pack3`, `settle3`, and `policy3` using only
  custom instruction encoding space.

The coprocessor path comes first because it measures the primitive without
committing to an ISA too early.

### H3 — ASIC exploration

After physical FPGA evidence, run RTL-to-GDS design-space exploration and
compare power/performance/area across lane counts. No tapeout decision is
justified before the end-to-end CPU comparison passes.

## Next implementation boundary

1. flash the exact 25 MHz and 75 MHz bitstreams and record separate SHA-bound
   `on_chip_self_test` measurements;
2. verify 75 MHz PLL lock, continuous epochs, temperature, and board power;
3. add on-device consequential-result filtering so the external interface does
   not inherit the 21.3 GB/s complete-result boundary;
4. implement host-fed counters and run one real transition-heavy workload on
   the same host CPU;
5. include transfer/setup, power, and p99 latency, then invoke
   `--require-competitive` before promoting any CPU claim.
